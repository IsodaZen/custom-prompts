# PR知見オーケストレータ（orchestrate）

複数日分の知見抽出を並列化し、**書き込みを1箇所に集約する。**

## 使いどころ

| 状況 | 使うスキル |
| :--- | :--- |
| 単一日 | `pr-knowledge:collect` を直接 |
| 2日以上、または期間指定 | このスキル |
| 初期セットアップ | `pr-knowledge:init` |

対象が1日だけなら並列化の利益がない。**このスキルを使わず `pr-knowledge:collect` を直接呼ぶ。**

## 引数

```
$pr-knowledge:orchestrate 2026-08-01..2026-08-31
$pr-knowledge:orchestrate 2026-08-25 2026-08-26 2026-08-27
```

- 期間指定は日単位に展開する。
- **展開結果が1日だけなら並列化の利益がないので、`pr-knowledge:collect` をファイル更新モードで直接実行し、その旨を報告する。** ワーカーを起動しない。
- **対象が指定されていない場合は、今日や「先週」を推測せず必ず確認する。**
- PRが存在しない日（土日、休日）も展開対象に含めてよい。ワーカーが0件で返す。

## 責務の分担

| フェーズ | 担当 |
| :--- | :--- |
| 対象の展開・分割 | オーケストレータ |
| PR取得・差分/議論の読解・知見抽出 | ワーカー（`pr-knowledge:collect` 返却モード） |
| 重複統合・矛盾解決 | オーケストレータ |
| ファイル書き込み・index更新 | オーケストレータ**のみ** |

**ワーカーは1バイトも書き込まない。** これが並列化の唯一の安全条件。

## 手順

### 1. 事前確認

```bash
git rev-parse --show-toplevel
gh auth status
cat .knowledge/config.json
git status --porcelain .knowledge/
```

- `config.json` が無い / パース不可 / `schema_version` が `1` でない → `pr-knowledge:init` を促して停止する
- `.knowledge/` に未コミットの変更がある場合は、**実行前にユーザーへ知らせて確認を取る。** マージ結果と混ざると切り分けが困難になる
- **続行する場合は `git status --porcelain .knowledge/` の出力をベースラインとして記録しておく。** 手順4の違反検知はこのベースラインとの差分で判定する。記録を怠ると、既存の未コミット変更をワーカーの違反と誤判定する
- `gh api rate_limit` で残枠を確認する。ワーカーは各PRごとに3回以上API呼び出しを行うため、残枠が少なければ並列数を下げるか実行を見送る

### 2. 分割する

対象日を1日1ワーカーに割り当てる。

**同時実行数は3〜5に抑える。** 上げても律速はGitHub APIのレート制限側で、コンテキストとレート枠を無駄に食うだけ。対象が30日あるなら、5並列×6バッチのように分割して順に流す。

**バッチ間では書き込まない。全バッチの回収が終わってから、手順5〜6を1回だけ実行する。** ワーカーは実行時点の `.knowledge/` を読んで `existing_file` を判定するため、途中で書き込むとバッチごとに前提がズレ、同じテーマが新規と更新に二重計上される。

各バッチの開始前に `gh api rate_limit` を再確認する。残枠が尽きかけていれば、そこまでの結果を確定させて残りを未処理として報告する。**枯渇したまま走らせて全ワーカーを失敗させない。**

### 3. ワーカーを起動する

各ワーカーへの指示は以下の契約を満たすこと。**サブエージェント起動の具体的な方法は実行基盤に依存するため、ここでは契約だけを定める。**

- `pr-knowledge:collect` スキルを使うこと
- 対象日を1つだけ渡すこと
- **返却モードで動くこと**（「ワーカーとして呼ばれている」「書き込まずにJSONで返して」を明示）
- `pr-knowledge:collect` の既定JSONスキーマで返すこと
- `.knowledge/` は読み取りのみに使うこと

ワーカーには他ワーカーの担当日や結果を渡さない。重複は後段で処理する。

### 4. 結果を回収する

各ワーカーから以下を受け取る。

- `findings[]`（`type` / `title` / `body` / `sources` / `existing_file` / `operation` / `conflicts_with_existing` / `status`）
- `deferred[]`
- `prs_examined` / `prs_skipped` / `prs_failed[]`

**ワーカーの失敗で全体を止めない。** 応答が無い、JSONとして壊れている、途中で落ちたワーカーは、その日を「未処理」として記録し、残りの結果でマージへ進む。未処理日は最終報告で明示し、再実行を促す。

回収後、**書き込み前にもう一度 `git status --porcelain .knowledge/` を確認し、手順1のベースラインと比較する。** ベースラインに無い差分が出ていればワーカーが契約に違反して書き込んでいる。その場合は停止し、どのファイルが変わったかを添えて報告する。

### 5. マージする

**必ず日付の昇順で処理する。** 完了順ではない。時系列が狂うと、古い知見が新しい知見を上書きする。

#### 5-1. 重複の統合

`type` と扱う対象が同一の findings を1グループにまとめる。判定基準は `pr-knowledge:collect` の「同一テーマの判定基準」に従う。

グループ内での統合:

- `sources` は全件を日付昇順で結合する
- `body` は重複記述を落として1本にまとめる。同じことを別の日のPRが裏付けている場合、記述は増やさず `sources` だけ増やす
- `status` は1件でも `draft` があれば、確度が確認できるまで `draft` を維持する
- `title` / `description` は最新日のものを採用する

#### 5-2. 矛盾の解決

`conflicts_with_existing` が付いた findings と、グループ内で内容が矛盾する findings を処理する。

- **本文は最終状態（最も新しい日付）に揃える**
- 途中の変遷は `## 変更履歴` に日付昇順で1行ずつ積む
- 同一日のPR同士が矛盾している場合は自動解決せず、両論をユーザーに提示して判断を仰ぐ

#### 5-3. deferred の統合

複数日から同趣旨の `deferred` が出た場合は1件にまとめ、`reason` と出典日を併記する。**同じ論点が繰り返し保留されている事実自体が情報**なので、件数を残す。

#### 5-4. 操作の確定

グループごとに `create` / `update` / `supersede` を確定する。複数ワーカーが同じテーマに `create` を返していても、**書き込みは1ファイルにまとめる。**

### 6. 書き込む

`pr-knowledge:collect` の手順6と同じ規則に従う。

- 新規は `_template.md` をコピーして埋める
- `updated` はそのファイルに反映した最新日
- ディレクトリは `config.json` の `types[].dir`。新設しない
- `index.md` は全ファイル書き込み後に**1回だけ**更新する。見出しは `types[].label`、前文は保持

**書き込みは逐次実行する。** ここを並列化しない。

途中で失敗した場合は**ロールバックしない。** どこまで書き込んだかをファイル単位で報告し、未反映分をユーザーに提示する。変更はワーキングツリーに残っているので、`git checkout -- .knowledge/` で破棄するか、続きから手で反映するかはユーザーが選べる。

### 7. 報告する

- 対象期間と展開した日数、うち処理成功 / 未処理の内訳
- 日付ごとの `prs_examined` / `prs_skipped` / `prs_failed`
- 新規作成ファイル一覧
- 更新ファイル一覧と、変更内容の一行説明
- **マージで統合した件数**（複数日から同一テーマが出たケース）
- 自動解決せずユーザー判断に回した矛盾
- `deferred` の集約結果
- 未処理日がある場合の再実行コマンド（例: `$pr-knowledge:orchestrate 2026-08-03 2026-08-07`）
- 書き込みが途中で失敗した場合は、反映済み / 未反映のファイル一覧

## 禁止事項

- **ワーカーに書き込みを許可しない**
- **書き込みフェーズを並列化しない**
- **完了順にマージしない。** 必ず日付昇順
- **`.knowledge/` の外を書き換えない**
- **コミットしない。** 変更はワーキングツリーに残す
- **バッチごとに書き込まない。** 全バッチ回収後に1回だけ
- **未処理日を黙って捨てない**
- **ワーカーが返さなかった知見を推測で補完しない。** 未処理日を自分で処理し直す場合は、その旨を明示して報告する
